# 基于约束细化图的项目决策管理方案

本文档描述一种面向多主体协作开发的项目决策管理方案，以约束细化图（Constraint Refinement Graph, CRG）为核心决策资产，并围绕它定义任务界定、任务执行、任务完成与审查以及维护机制。

## 1. 决策资产层：约束细化图

在项目仓库中以版本化文本维护一张约束细化图（Constraint Refinement Graph, CRG）。

CRG 记录项目已经作出的、会限制后续实现选择空间的决策，以及使这些决策成立的项目事实。

在本方案语境下，"约束"与"项目决策"同义，均指已作出且会限制后续选择空间的决定。后文使用"约束"一词时，取此含义。

项目实现总体上是从抽象走向具体的过程，其抽象极限可以理解为项目核心意图，具体极限则是源码实现。CRG 只覆盖其中值得长期记录和维护的一部分。

约束之间的上下游关系通过边表达，边的方向从抽象指向具体。

## 1.1 节点类型

CRG 包含两类节点：约束节点（Constraint Node）和前提节点（Premise Node）。

### 约束节点

约束节点表示项目已经作出的、会限制后续实现选择空间的决策。

约束节点包含四个属性：

- 摘要（Summary）：内容的简短概括，用于遍历时快速判断节点相关性、节约上下文长度
- 内容（Content）：该决策具体规定什么
- 理由（Rationale）：可选的独立属性，完整记录得出该决策的推导与权衡过程。对有依据的约束，说明为什么从这些依据得出该决策；对根约束，说明该约束为什么被项目接受
- 依据（Grounds）：细化出该决策的输入集合，可包含约束节点和前提节点

根约束的依据集合为空，其理由因此说明该约束为什么被项目接受。理由是可选属性：当决策的自明性足够高时，可以省略。

一个约束节点可以有多个依据（包括约束和前提），也可以作为依据出现在多个下游约束的依据集合中。

### 前提节点

前提节点表示项目运作所依赖的客观事实。此处"前提"特指已确认的项目事实。

前提节点记录事实内容及与事实相关的客观属性，例如：

- 摘要：同约束节点，用于快速判断相关性
- 事实内容
- 来源
- 最后确认时间

前提的使用状态由图结构自然表达：被约束节点的依据集合引用即为已使用。前提无论是否被引用，均默认注入任务上下文（见 2.2）。

## 1.2 边

CRG 中只有一种边，方向从抽象到具体：

> **(约束 | 前提) → 约束**

当源节点是约束时，该边表示上游决策细化为下游决策。当源节点是前提时，该边表示客观事实支撑下游决策。二者是同一种边，区别由源节点类型自然表达。

边的唯一属性是方向。细化的理由和事实条件均记录在目标约束节点的依据和理由属性中。

边所构成的约束→约束路径保持无环，从而保证约束具有明确的抽象—具体方向。前提节点入度为零，独立于约束路径的无环性约束。

## 1.3 图的上界

本文的"上界"与"下界"取图示的空间含义：上为抽象端，下为具体端，不是序理论意义上的上界与下界。

CRG 的上界是一组根约束（Root Constraint），即入度为零的约束节点。

根约束代表项目必须在其内部运行的最高层决策，例如：

- 项目目标与愿景；
- 外部合规要求；
- 不可逆或高成本的技术选型；
- 商业与运营约束。

根约束的修改需要项目最高级别的授权。

## 1.4 图的下界

CRG 的下界由决策是否具有长期约束价值决定；下界不是一组特定节点，而是一条入图价值判据。

一个决策适合进入 CRG，当它会持续限制未来任务的选择空间。

可使用以下判据辅助判断。

### 选择空间判据

如果一个决策排除了部分实现方案，但仍保留多个合理选择，则它适合进入 CRG。

当某个决策已经成为代码中唯一自然的实现细节时，通常无需作为约束单独记录。

### 违反代价判据

违反后需要重写架构、跨模块修改或产生较大范围影响的决策，应倾向于进入 CRG。

对于违反后只需修改当前文件、且编译器、类型系统或测试能够立即发现违反的决策，通常无需进入 CRG。

### 变更频率判据

每个 commit 都可能变化的实现细节通常无需进入 CRG。

该判据主要用于回顾性清理。

CRG 下方存在未约束细化空间（Unconstrained Refinement Space）。对于没有被 CRG 明确决定的实现选择，当前主体可以根据任务自行决策。

## 1.5 前提的入图判据

只有对项目决策具有实际影响的项目特有事实才需要进入 CRG。

优先考虑：

- 主体无法从通用知识中获知的项目特有事实；
- 与主体通常默认假设相矛盾的项目事实；
- 发生变化后可能导致已有决策需要重新审查的事实。

通用语言语义、协议规范和框架常识属于通用知识，无需重复记录；仅当项目实际使用的版本、配置与通用认知存在差异时，差异本身才需要作为前提记录。

实际筛选时，可以适当偏向保留项目特有事实，因为遗漏未知事实的代价通常高于重复提供已知事实的代价。

## 1.6 前提变化

当已引用的前提发生变化时，应沿该前提的出边找到直接依赖它的约束节点，并将这些约束标记为待审查（Pending Review）。审查导致的约束修改若继续影响下游，按 3.2 的下游检查规则逐级处理。

前提变化触发相关约束的审查流程。具体影响的判定和约束的修改在相应授权下完成。

未被引用的前提没有出边，因此不会通过前提变化自动触发约束审查。

长期未确认的前提应通过定期维护进行复核。

## 2. 任务界定层

## 2.0 主体与授权

本方案的权限模型以主体被授予的决策修改权限为依据。主体（Actor）泛指任何参与读取或修改 CRG 的实体，包括人类、自治系统或二者的组合。

任务在进入执行状态前，会被赋予一个授权上下文（Authorization Context），其中包含本次任务的作用域锚点与冻结区。本方案仅依据该上下文对当前主体的操作进行校验。

授权上下文由治理或编排系统在任务创建时签发，签发本身须满足目标节点的授权级别要求（例如修改根约束需要项目最高级别的授权，见 1.3）。

权限校验统一依据授权上下文进行：约束与前提的修改机制相同，目标位于冻结区即拒绝修改并进入越界升级（见 3.4），冻结区以外可以自行修改。任务执行中发现前提有误或过时，可更新前提，但须按 1.6 标记下游待审查，并通过正常 Git 流程审核。任务边界之外的前提维护（见第 5 节）不受任务授权上下文约束。

## 2.1 作用域锚点（Scope Anchor）

每个任务包含一个或多个作用域锚点（Scope Anchor），即任务开始时需要加载的 CRG 节点。

作用域锚点决定当前主体开始任务时默认加载的项目决策上下文。

当前主体在任务执行过程中可访问 CRG 中的任意节点，包括：

- 沿入边向上追溯祖先约束；
- 横向查看其他约束分支；
- 沿出边向下查看已有细化；
- 查看相关前提。

## 2.2 前提注入

全部前提默认注入任务上下文，无论其是否已被约束引用。前提因此可以独立于决策谱系保存，无需预先挂接即可参与任务。

前提规模过大时，可由编排系统按任务收窄注入范围。如何选择要收窄的前提属于编排系统的职责，不属于本方案的核心机制。

## 2.3 按需遍历

当前主体可以根据任务需要主动遍历 CRG。

遍历时可以先读取节点的摘要，根据摘要判断节点是否相关，再读取完整的内容、理由和依据。

当前主体沿边逐步恢复所需背景，按需加载决策上下文。

## 2.4 冻结区（Frozen Zone）与修改空间

每个任务包含一个冻结区（Frozen Zone）：任务执行期间不得修改的节点集合。授权上下文通过指定若干约束来确定冻结区，冻结区即这些约束连同其全部祖先节点（约束与前提）。冻结区由其中最下游的约束——下游不再属于冻结区的约束——唯一确定，它们是冻结区的最小表示。

修改空间（Modification Space）是冻结区的补集：冻结区以外的全部约束都在修改空间以内。冻结区沿依据向上封闭，修改空间因此沿细化方向向下封闭——修改空间以内约束的下游细化仍在修改空间以内。当前主体可以在修改空间以内修改约束或新增细化，任务中新增的节点属于修改空间。修改导致下游约束失效时，应在同一变更中一并修复；失效的下游约束必属修改空间，修复不涉及越界授权。

冻结区内的节点：

- 当前主体可以读取；
- 当前主体可以基于其进行推理；
- 当前主体在当前授权范围内无权修改。

作用域锚点与冻结区相互独立：

- 作用域锚点决定初始加载什么；
- 冻结区决定当前主体不可以改变什么，冻结区以外皆可改变。

未显式指定冻结区时，默认取全部根约束（见 1.3）连同其祖先。

## 3. 任务执行层

## 3.1 约束与前提注入

任务执行时，将任务所需的 CRG 内容提供给当前主体。

其中：

- 约束是必须满足的项目决策；
- 前提是执行决策时需要考虑的客观事实。

违反约束意味着产出不符合项目决策。

前提为执行决策提供事实基础。忽略前提可能导致方案不可行，或使相关约束的依据失效。

## 3.2 约束演化

如果当前约束集合无法容纳任务，当前主体可以在修改空间以内调整约束。

调整应遵循最小修改原则：

1. 定位阻挡任务的约束；
2. 理解该约束的依据和理由，以及其上游约束的设立背景；
3. 判断哪些局部修改可以解除阻碍；
4. 优先选择对已有决策和下游约束影响较小的方案；
5. 将修改作为普通项目变更进入现有 Git 审核流程。

修改约束时，应沿该约束的出边检查其下游约束，判断修改是否导致下游细化失效。失效的下游约束必在修改空间以内（见 2.4 的封闭性），应在同一变更中一并修复。

约束修改的目的是在授权范围内继续演化项目的决策空间。

## 3.3 冲突（Conflict）

冲突（Conflict）指两个或多个约束在当前条件下无法同时满足的矛盾。

冲突成立的判定标准：不存在能够同时满足相关约束的方案。

成本与性能之间的权衡、不同设计目标之间的优化问题、多个可行方案之间的选择，只要仍然存在能够同时满足相关约束的方案，即属于正常的设计取舍，通过约束细化流程处理。

当前主体可以在执行过程中发现冲突，包括：

- 当前任务与已有约束冲突；
- 不同约束之间发生冲突。

前提变化可能使原本可以共存的约束变得互斥，从而暴露冲突；但前提变化导致的依据失效本身不是冲突，按 1.6 的待审查流程处理。

发现冲突后，当前主体应根据：

- 约束的上下游关系；
- 相关约束的理由；
- 相关前提；
- 当前任务目标；

进行局部推理，决定是否以及如何调整约束。

如果调整涉及冻结区，则必须进入越界升级流程。

## 3.4 越界升级（Boundary Escalation）

如果任务无法在当前修改空间以内完成，且阻挡因素位于冻结区，当前主体必须停止对相关约束的修改，并触发越界升级（Boundary Escalation）。

升级时应说明：

- 阻挡任务的约束及其图上的位置；
- 为什么当前修改空间以内不存在可行方案；
- 建议如何修改相关约束；
- 修改可能影响的下游约束；
- 是否存在边界内的替代方案及其代价。

接收升级的主体可以：

- 扩大当前任务的修改空间；
- 在相应授权下修改冻结区约束；
- 调整任务范围；
- 终止任务。

升级对象的选择、升级后的审批流程和合并规则由项目治理与编排系统定义。

冻结区是已确定、当前主体无权改变的项目决策；冻结区以外是当前主体被授权继续探索、细化和修复的决策空间（修改空间）。

## 4. 任务完成与审查

任务完成后，需要分别回答两个问题。

## 4.1 产出是否满足相关约束

对最终产出进行必要的代码层检查，例如：

- 测试；
- 静态分析；
- 类型检查；
- 架构规则检查；
- 代码审查。

目的是判断最终实现是否违反任务涉及的项目约束。

具体使用哪些检查机制由项目现有工程体系决定。

## 4.2 决策是否需要更新

如果执行过程中：

- 修改了已有约束；
- 新增了会持续限制未来选择空间的决策；
- 改变了已有约束的依据或理由；

则应判断这些变化是否具有长期约束价值、是否需要更新 CRG。

需要长期保留的决策应更新 CRG，并通过正常 Git 工作流进行审核。

对于约束修改，还应审查其与上游依据及相关前提的关系是否仍然合理，以及是否导致已有下游约束失效。

CRG 记录项目已经接受的决策及其决策谱系。

## 5. 维护

CRG 是项目决策的长期资产，其维护成本需要与传统设计文档的维护成本进行实际比较。

维护工作包括：

- 判断新的项目决策是否应进入 CRG；
- 删除不再具有长期决策价值的约束；
- 更新发生变化的前提；
- 审查前提变化导致的待审查约束；
- 定期复核长期未确认的前提；
- 回顾执行过程中的决策是否产生了应当沉淀的新约束。

维护协议应明确：

- 责任主体；
- 触发维护的事件；
- 定期审查周期；
- 约束和前提的生命周期规则。

本方案的价值在于将值得长期保留的项目决策组织成可追溯、可按需访问、可受权限约束地继续细化的结构，从而降低理解项目决策、追踪决策变化和进行错误修改的成本。

## 6. 核心原则

1. CRG 记录项目已经作出的、会限制后续选择空间的决策，以及使这些决策成立的项目事实。
2. Constraint 表示项目决策，Premise 表示客观事实。二者在 CRG 中含义明确、不可互换。
3. 约束之间的上下游关系通过边的方向（从抽象到具体）表达。
4. 边表示项目认可的决策具体化关系，细化的理由和事实条件记录在目标约束节点的依据和理由属性中。
5. 约束节点的理由是独立且可选的属性；摘要是独立于内容的属性，用于遍历时快速判断相关性、节约上下文长度。
6. Premise 特指已确认的项目事实，其使用状态由图结构自然表达。
7. 约束→约束路径保持无环，前提节点入度为零；由此可推出整图必然无环。
8. 作用域锚点决定初始加载什么，冻结区决定当前主体不可以改变什么；修改空间是冻结区的补集。
9. 当前主体可以访问整个 CRG，在修改空间以内继续细化或修改项目决策。
10. 冲突指无法同时满足的真正矛盾，设计取舍通过约束细化流程处理。
11. 冲突处理由当前主体根据决策结构和具体情境进行局部推理。
12. 当任务无法在修改空间以内完成、且阻挡因素位于冻结区时，当前主体应停止修改并触发越界升级。
13. 本方案支持对 CRG 的按需遍历和渐进式知识披露。
14. CRG 的上界由图结构定义，即入度为零的根约束；下界由决策的长期约束价值决定。
15. 本方案的权限模型以主体被授予的决策修改权限为依据，与主体的具体身份无关。任何具有相应权限的主体均可维护、修改或继续细化 CRG。
16. 越界升级的对象、审批流程和合并规则由项目治理与编排系统定义。
17. 本方案的最终价值取决于：维护 CRG 的成本是否低于它所节省的成本——理解项目决策、追踪决策变化和修正错误的成本。
