# 决策谱系图（DLG）

决策谱系图（Decision Lineage Graph, DLG）是一种面向多主体协作开发的项目决策管理方案：在项目仓库中以版本化文本维护一张图，记录项目已经作出的、会限制后续实现选择空间的决策，以及使这些决策成立的项目事实。它同时是多主体协作中的边界资产：任务按授权上下文界定，冻结区之外的决策空间可以在授权范围内继续细化。本方案的价值取决于：维护 DLG 的成本是否低于它所节省的成本——理解项目决策、追踪决策变化和修正错误的成本。

## 节点与边

DLG 包含两类节点。

**决策节点**表示项目已经作出的、会限制后续实现选择空间的决策，属性包括：

- 摘要：内容的简短概括，用于遍历时快速判断相关性、节约上下文长度；
- 内容：该决策具体规定什么；
- 理由：可选，记录从依据得出该决策的推导与权衡，表达推理本身、不复述前提中的事实；决策自明时省略；
- 依据：作出该决策的依据集合，可包含决策与前提；根决策的依据为空；
- 探索中：可选布尔，缺省为定案。决策分定案与试行两个成熟度层级，标记探索中的决策是当前工作线的试行承诺，预期可能被替换或撤销。

**前提节点**表示项目运作所依赖的已确认客观事实，属性包括摘要、事实内容与最后确认时间。事实内容记录事实本身，不书写日期——时间信息由最后确认时间承载。前提在定义上即已确认，不设探索中属性；其使用状态由图结构自然表达（被决策的依据引用即为已使用），无论是否被引用均默认注入任务上下文。

探索中的生效状态在读时派生：决策自身标记探索中，或其任一（传递）依据决策生效探索中，即为生效探索中。上游探索中时下游细化自动处于探索中；上游定案后子树随之自动定案。依据探索中时下游决策无法显式定案；与候选选择无关、可在任一方案下定案的决策，应挂接到已确定的依据上。

边只有一种，方向从抽象指向具体：**(决策 | 前提) → 决策**。源为决策表示上游决策细化为下游决策，源为前提表示客观事实支撑下游决策，二者是同一种边。边的唯一属性是方向：细化的理由与事实条件记录在目标决策的依据和理由属性中，不标注在边上。边的方向表达抽象层级关系，不表达决策确定的时间顺序——下游可先于上游入图，上游也可在下游细化积累之后定案，此时通过更新下游的依据完成挂接。决策→决策路径保持无环，前提入度为零，因此整图无环。

## 图的边界

**上界**是一组根决策（依据为空的决策）：项目必须在其内部运行的最高层决策，如项目目标与愿景、外部合规要求、不可逆或高成本的技术选型、商业与运营决策。根决策的修改需要项目最高级别的授权。

**下界**不是一组特定节点，而是一条入图价值判据：决策适合进入 DLG，当它会持续限制未来任务的选择空间。辅助判据：

- 选择空间：排除了部分方案但仍保留多个合理选择的决策适合入图；已成为代码中唯一自然实现细节的决策无需记录；
- 违反代价：违反后需要重写架构、跨模块修改或产生大范围影响的应倾向入图；违反后只需修改当前文件且编译器、类型系统或测试能立即发现的无需入图；
- 变更频率：每个 commit 都可能变化的实现细节无需入图（主要用于回顾性清理）。

DLG 下方存在未决细化空间：未被 DLG 明确决定的实现选择，当前主体可根据任务自行决策。

**前提入图判据**：只有对项目决策具有实际影响的项目特有事实才入图——主体无法从通用知识获知的、与通常默认假设相矛盾的、发生变化后可能导致已有决策需要重新审查的事实。通用语言语义、协议规范、框架常识属于通用知识，无需记录；仅当实际使用的版本、配置与通用认知存在差异时，差异本身才作为前提记录。筛选时偏向保留：遗漏未知事实的代价通常高于重复已知事实。

## 任务界定

**主体与授权**：主体泛指任何参与读取或修改 DLG 的实体，包括人类、自治系统或二者的组合。任务进入执行前被赋予授权上下文，包含作用域锚点与冻结区，由治理或编排系统在任务创建时签发，签发本身须满足目标节点的授权级别要求（如修改根决策需要最高级别授权）。权限校验统一依据授权上下文：目标位于冻结区即拒绝修改并进入越界升级，冻结区以外可自行修改。权限模型以修改权限为依据，与主体身份无关。

**作用域锚点**是任务开始时默认加载的节点，决定初始上下文。主体在任务执行中可访问任意节点：沿入边向上追溯祖先、横向查看其他分支、沿出边向下查看细化、查看前提。

**前提注入**：全部前提默认注入任务上下文，无论是否已被引用，前提因此可独立于决策谱系保存、无需预先挂接。规模过大时由编排系统收窄注入范围，收窄策略属于编排系统职责，不属于本方案核心机制。

**按需遍历**：主体可根据任务需要主动遍历 DLG，先读摘要判断相关性，再展开完整内容、理由与依据，沿边逐步恢复所需背景。

**冻结区与修改空间**：冻结区是任务执行期间不得修改的节点集合，由授权上下文指定的若干决策连同其全部祖先（决策与前提）构成，由其中最下游的决策——冻结前沿——唯一确定。修改空间是冻结区的补集：冻结区沿依据向上封闭，修改空间沿细化方向向下封闭，修改空间内决策的下游细化仍在修改空间内，修改导致的下游失效必落在修改空间内，可在同一变更中一并修复而不触及越界授权。冻结区内的节点可读取、可基于其推理，但当前授权下无权修改。未显式指定冻结区时，默认取全部根决策连同其祖先。

## 任务执行

**注入**：决策是任务必须满足的项目决定，前提是执行决策时需要考虑的客观事实。违反决策意味着产出偏离项目已作出的决定；忽略前提可能使方案不可行，或使相关决策的依据失效。生效探索中的决策以试行身份注入，与定案决策明确区分标注；试行期间获得的可复用知识应沉淀为前提，而非依赖决策本身存续。

**决策演化**：当前决策集合无法容纳任务时，主体可在修改空间内调整决策，遵循最小修改原则：定位阻挡任务的决策，理解其依据、理由与上游决策的设立背景，判断哪些局部修改可以解除阻碍，优先选择对已有决策和下游决策影响较小的方案，并将修改作为普通项目变更进入现有 Git 审核流程。修改决策时沿出边检查下游是否失效，失效的下游决策必在修改空间内，应在同一变更中一并修复。

**冲突**：冲突指两个或多个决策在当前条件下无法同时满足的矛盾，判定标准是不存在能够同时满足相关决策的方案。冲突仅在生效状态均为定案的决策之间判定：互斥的探索中决策（如同一细化位置的兄弟候选）是备选方案；探索中与定案决策之间的矛盾属于探索反馈，按决策演化处理；只要仍存在能够同时满足相关决策的方案——成本与性能的权衡、不同设计目标间的取舍、多个可行方案的选择——即属正常设计取舍，通过决策细化流程处理。发现冲突后，主体依据决策的上下游关系、相关决策的理由、相关前提与当前任务目标做局部推理，决定是否以及如何调整；调整涉及冻结区时进入越界升级。

**越界升级**：任务无法在当前修改空间内完成且阻挡因素位于冻结区时，主体必须停止对相关决策的修改并触发升级，向授权上下文的签发方（或治理系统指定的接收方）提交升级报告，说明：阻挡任务的决策及其图上位置、为什么修改空间内不存在可行方案、建议如何修改相关决策、修改可能影响的下游决策、是否存在边界内的替代方案及其代价。工具层与存储层拒绝越界写入时返回的结构化报告是升级报告的素材与载体，本身不构成裁决。接收方可以扩大当前任务的修改空间、在相应授权下修改冻结区决策、调整任务范围或终止任务；升级对象、升级后的审批流程和合并规则由项目治理与编排系统定义。

## 审查与维护

任务完成后回答两个问题。

**产出是否满足相关决策**：通过测试、静态分析、类型检查、架构规则检查、代码审查等手段判断最终实现是否违反任务涉及的决策；具体使用哪些检查机制由项目现有工程体系决定。

**决策是否需要更新**：执行中修改了已有决策、新增了会持续限制未来选择空间的决策、改变了已有决策的依据或理由、将探索中的决策转正的，应判断这些变化是否具有长期决策价值并更新 DLG，经正常 Git 工作流审核。决策修改还应审查其与上游依据及相关前提的关系是否仍然合理、是否导致已有下游决策失效；转正是修改空间内的普通写入，仍须履行下游检查义务。

前提变化时，沿该前提的出边找到直接依赖它的决策并标记为待审查，审查导致的决策修改若继续影响下游，按决策演化的下游检查规则逐级处理；未被引用的前提没有出边，不会自动触发审查。长期维护包括：判断新决策是否入图、删除不再具长期决策价值的决策、删除探索中决策前将其中可复用的发现沉淀为前提（决策会被替换，事实不会）、更新发生变化的前提、审查待审查决策、定期复核长期未确认的前提。维护协议应明确责任主体、触发事件、审查周期与节点生命周期规则；维护成本应与传统设计文档的实际维护成本进行比较。
