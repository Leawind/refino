## 技术形态与边界

- **核心 Rust 化**：引擎与存储以 Rust 实现，是图逻辑与存储格式的唯一实现，TypeScript 侧不设第二份实现。
- **全 wasm 统一**：核心编译到 wasm，浏览器与 Node 共用同一产物；不引入 napi 等第二边界技术。唯一的原生产物是命令行二进制（npm 平台包与 crates.io 双渠道分发）。
- **Io 注入**：存储核心不含文件系统与时钟实现，文件系统操作收敛为同步 Io trait，由宿主注入；外部文件事件由宿主推入，核心保持全同步语义。
- **边界形状**：`@refino/wasm` 的 TS 门面产出 JS 原生形状，与既有 TS 包签名同构，消费方只更换 import 来源、不改逻辑。
- **wire 类型单一来源**：跨语言 wire 类型由 Rust 结构体定义、生成 TS 定义（产物入库），两端契约不可漂移。
- **性能分层**：Node 侧 fs 调用次数与移植前持平，解析与图计算在 Rust 内提速；大规模图的性能上限由原生二进制承担。

## 引擎纯净性

引擎专指 `refino-core`：不含文件系统、时钟与网络依赖，全部为纯逻辑，wasm-clean；随机数来自注入的随机源。DLG 的存储格式不是引擎职责，由 `refino-storage` 定义并实现，引擎只消费其产出的内存图；引擎类型不携带存储路径，文件路径由存储层依"路径即身份"规则从 `(id, type)` 推导；节点内容（正文、理由）不是引擎类型的组成部分，内容缺席不影响任何拓扑操作。

## 渐进披露与常驻集

图可能达到 10⁶ 节点规模；无论命令行、agent 工具还是网页端，都需要在理解"这个节点是什么"的前提下判断下一步披露什么。引擎内存模型按"常驻 + 分页"划分：

- **常驻集**是引擎类型的全部内容：id、type、summary、grounds、children，及 premise 的 confirmed 与 decision 的 exploring。type 承载边语义与授权边界；summary 是渐进披露的入口；grounds 是边关系的语义权威，children 是图内派生的反向索引；confirmed 与 exploring 的文件表示与内存表示的转换由存储层在文件边界完成；exploring 的生效状态（沿依据闭包派生）不存储、读时计算。
- **分页集**不经引擎内存，按 id 由存储层按需供给：正文与理由。持久化介质多样且未必支持 O(1) 邻接查询，因此拓扑与摘要必须常驻并建索引，内容容忍按需加载的延迟。
- **投影语义**：引擎图是存储的只读投影，权威数据在存储；写路径 = 经存储落盘 → 以引擎变更原语增量更新投影。内容取数、缓存与失效由存储层与各消费方负责，引擎对此一无所知。

## 错误码归属

issue 与错误携带的 `code` 是对外的 wire 值（字符串，非封闭集合），由产生方定义：引擎定义图级语义码，存储层定义存储格式码，各请求处理层自行定义请求形状码、不得借用他方的码。issue 的归属字段同样由产生方定义——引擎 issue 不含文件路径；持久化层 issue 对未能解析出节点的文件额外携带文件路径（此时路径是唯一可靠的定位）。

## 引擎提供的共享原语

以下原语由引擎统一提供，供 CLI、Web API、harness 等所有消费方复用：

- **批量查询的部分成功语义**：标准结果形状按查询 id 分组返回；部分 id 不存在时其余 id 仍返回完整结果，缺失以错误条目标注。所有批量查询接口（CLI、harness 工具、Web 按需查询）均使用此形状。
- **写入前 grounds 校验**：对当前图校验一次 grounds 变更（引用不存在、成环等）；所有写入路径在落盘前调用，确保图级校验逻辑单一来源。

## 存储层 Store

长驻消费方需要在内存中维护与磁盘一致的常驻投影；"写完落盘后忘记更新投影"与"API 写入和外部文件事件走两套更新逻辑"是这一模式的固有风险。`refino-storage` 提供有状态的 Store，把投影一致性收敛到变更发生的同一处：

- 职责：常驻投影、内容分页缓存、issue 缓存、单调递增 revision、变更监听接入；
- 写入方法内部完成校验 → 原子写 → 投影增量应用 → issue 复检 → 广播；校验失败即拒绝写入，消费方无法绕过校验直接写文件；
- API 写入与外部文件事件走同一增量入口，抑制 no-op 回声；
- 变更事件携带变更集、受影响下游（待审查原料）与变更来源；待审查集的累积策略与展示语义由消费方定义，Store 不持有；
- watch 可选：一次性消费方（CLI）不监听；长驻消费方开启后，外部变更自动进入同一增量入口。

CLI、Web 服务与工具插件一律经 Store 访问 `.refino/`，不再各自维护投影。

## 节点内容

- 节点正文使用 markdown，允许已被广泛使用、LLM 能理解且能写出的常见扩展语法（mermaid、latex 等），不要求 UI 实现所有扩展语法的渲染。
- 摘要是独立于正文的属性，用于遍历时快速判断节点相关性、节约上下文长度；摘要在内存中常驻（见"渐进披露与常驻集"），如何随节点文件存储与维护（frontmatter 字段、缺省回退规则）是存储层的实现细节。

## 存储格式容错

frontmatter 中的未知字段一律静默忽略、不报告 issue；已知字段出现在错误类型的节点上同待遇。这保证存储格式可以在不破坏既有节点文件的前提下向前演进（新增字段时，旧版本仍能正常读取）。

由此得到一条硬不变量：**边只来自决策节点的 `grounds` 字段**——任何其他字段在任何一层（引擎、存储、查询、注入）都不产生边。

## 命令行工具

CLI 是自文档接口：agent 在没有其他上下文的情况下，仅凭 CLI 即可了解其概念、用法与注意事项。`refino guide` 输出面向 agent 的使用指南，文本单一来源在代码中、随 CLI 一同演进；`--help` 末尾指路 guide。refino 具体用法的唯一权威是所接入 harness 的工具说明与 refino 命令本身（guide、`--help`）；使用 refino 的项目不把 refino 用法复制进自身文档，以免随工具演进而失真。

CLI 不校验授权上下文（冻结区与越界概念属插件形态）：插件接管的会话中一律经插件工具读写，不得以 CLI 规避插件的写路径校验；guide 将此列为硬规则。

分发为单一原生二进制、双渠道同 tag 发布：npm 平台包模式与 crates.io。

## 任务层归属

任务界定概念（作用域锚点、冻结区、修改空间、授权上下文）以及冲突检测与越界升级，仅在与 vibe coding 工作流结合时才有意义，不进入引擎：由 `@refino/harness` 与各工具插件实现，引擎为其提供受影响决策集等纯图查询原语。生效探索状态（沿依据闭包的派生）同样是纯图查询，由引擎原语提供、读时派生不持久化，harness 消费其结果做注入标注。

## harness 与工具插件功能设计

集成 refino 后，agent 需要面向用户与 AI 模型两组能力。本节确定 `@refino/harness` 与工具插件的边界。

### 用户侧：授权上下文的签发

签发有两套机制：**对话签发**为基础，**授权控制台**为增强（后继课题）。对话签发只签冻结区——锚点是注入策略参数、由运行时自动推导（见"上下文注入协议"），不进入签发：模型为确定锚点须先知晓任务相关节点内容，属循环论证。

对话签发：模型凭图知识起草冻结区划分，在对话中向用户呈现草案与理由（冻结计数、解冻根决策警告等预演信息），经宿主的审批面获得人的明确批准后由工具落签。人只有对话，模型拥有协议，机器守住批准门：批准不可由模型伪造。

授权控制台：锚点与冻结区的选择统一为单个控制台组件，是"上下文编译器的前端"——人签发的授权上下文与模型收到的注入上下文是同一对象的两种投影；同一交互覆盖开局签发、任务中途调整与越界升级的裁决（升级的解法就是再签发）。组件属 `@refino/ui`，`@refino/harness` 提供状态模型；`refino web` 不挂载控制台，浏览域不含授权概念。

### 模型侧：DLG 访问工具

模型不通过直接操作 `.refino/` 文件访问 DLG，而是使用 harness 暴露的结构化工具：读取类（列表、搜索、节点详情、依据、祖先、受影响决策集、强兄弟）、待审查查询、写入类（新增、修改、删除）。关键语义：

- 查询工具尽量批量、部分成功（见"引擎提供的共享原语"）；
- 更新采用部分更新语义（省略的字段保持不变），grounds 整体替换并经校验，避免模型凭记忆重打未读取的正文；
- 写入前经授权上下文校验；越界（目标落在冻结区）即拒绝，并返回结构化升级报告（作为正常工具结果，非报错）。

### 上下文注入协议

- 初始注入：作用域锚点与全部前提，按两级策略渲染——先注入 summary，模型判定相关后再展开全文。锚点由运行时自动推导：图不超过自动锚点预算时取全部节点（初始注入即全图摘要），超预算时不注入全图摘要，代之以极简引导（图已连接、节点数、根决策摘要），模型以搜索定位任务相关节点。冻结区不整体枚举：注入随附协议声明（标注只读者属冻结区，未列出者属修改空间；试行者可能被替换或撤销），冻结与探索状态由读侧在每次渲染节点时原样标注。
- 模型可访问全图，但初始上下文只含锚点与前提，其余靠工具按需拉取；冻结状态不依赖初始枚举，写路径始终按生效授权强制校验。

### 增量更新与缓存友好

注入协议以缓存友好为决策：上下文分为稳定前缀（已注入的快照）与增量 delta，锚点/冻结区变化时只注入 delta 事件、不重述全量快照，保持前缀稳定以利用模型的 prompt cache；delta 作用于签发列表本身（锚点与冻结前沿），不展开祖先闭包——冻结区语义在读取时按图重新闭包。

**会话已知集**是外部变更通知的参照系：每个会话在内存中记录已进入模型上下文的节点信息（id、摘要、正文已交付标记、直接依据与下游快照、见时的 revision），磁盘变更仅对已知集内的节点计算字段级差分，在下一注入点以简洁文本报告；已知集外保持静默。已知集纯内存、随会话进程生灭、不整块注入；失败即软——只影响通知质量，不影响读正确性。待审查集独立于已知集派生：它是写安全机制（修改前复核上游），与模型读过什么无关，按变更源全量报告。

### harness 与工具插件的分工

- `@refino/harness`（平台无关）：任务界定纯图逻辑（授权上下文、冻结区计算、越界校验、升级报告）、上下文渲染与 delta 事件生成、待审查派生、注入协议抽象。
- 工具插件（特定宿主的薄适配）：会话初始化时加载 `.refino/` 并生成初始上下文，把读写能力注册为宿主工具，承接宿主绑定（审批面、注入通道）。

refino 接入 harness 的唯一方式是针对特定 harness 开发的插件，不设通用兜底接入方式。

### dsh 插件落地形态

dsh（DeepSeek 官方开源 agent harness，基于 Cordis，developer preview）的接入形态已定案：**以 Cordis 插件形式接入，以 dsh bundle（npm 包）形式分发**。进程内插件是多项接入需求的唯一满足形态：MCP 只桥接 tools，无法在会话初始化时注入锚点上下文，也没有推送通道；Skill 可捆绑受守卫的执行逻辑，但会派生第二份受守卫读写实现、造成漂移——受守卫的读写只有一份实现（Store 写路径），讲解性技能可作轻量补充。

- **默认授权上下文**：冻结区默认取全部根决策连同其祖先，前提全部注入，锚点按注入协议自动推导。签发后的授权上下文是**会话状态**：只存在于插件进程内存，不落任何文件；resume 后回落默认值或编排者凭据，并在恢复时注入一行当前授权状态，防止模型持有过期的授权认知。编排者凭据生效时插件拒绝一切签发——任务内授权不可自我扩张，改冻结区须回到签发者。
- **冻结区签发（对话签发）**：签署工具承载，经 dsh 原生审批服务请求人的明确批准：fail-closed，仅显式允许生效，无应答者或拒绝策略下一律拒绝并维持当前授权。批准即签署：会话内即时生效、以 delta 注入新冻结区、不落任何文件；会话内签发不跨 resume。
- **delta 注入降噪**：合并多批外部变更事件并设最小注入间隔；渲染文本是变更集合的纯函数，与上一次注入相同时不注入。
- **依赖策略**：dsh 处于 developer preview，依赖精确版本锁定（宿主版本一变即安装失败，fail-fast），对 dsh 的依赖面刻意收窄。

#### 采用契约

安装与采用是两层正交的事：工具安装（CLI、插件）是用户/机器级的，装了不意味着任何仓库都要用；采用是仓库级的，唯一信号是仓库内存在版本化的 `.refino/` 目录，随 git 提交、协作者克隆即继承。信号在两处执行：dsh 插件以定位到 `.refino/` 为激活前提，找不到则不接管；CLI 读写命令一律要求 `.refino/` 存在，缺失即拒绝并指路 `refino init`——采用是显式动作，模型不得在未采用的仓库中立户。

#### 不变量

refino 的全部产出 = DLG 节点（版本化）+ `refino init` 创建的 `.refino/` 骨架；除此之外，插件形态不产生任何状态文件，签发状态与已知集随会话进程生灭。`.refino/` 目录名专属仓库内 DLG 存储，不存在仓库外的用户级 refino 目录；refino 不探测任何 harness 的配置、技能或插件目录。

## 前端技术栈

可视化界面统一使用 Vue 3。`@refino/ui` 定位为"组件库 + 可嵌入的编辑器应用壳"，宿主（工具插件、桌面应用、VSCode webview）负责提供容器与数据通道。

## Web 界面（`refino web`）

`refino web` 是面向人类的 DLG 浏览、编辑与变更审阅工具，只提供对 DLG 本身的访问，与 agent 任务执行无关——作用域锚点选择、冻结区签发（授权控制台）等任务界定功能属于工具插件宿主的交互组件，不在本界面范围内。界面结构、页面与交互细节见 `@refino/ui` 的 [DESIGN.md](../packages/ui/DESIGN.md)。

### 技术选型

组件库选用 Naive UI：TypeScript 支持与 tree-shaking 最好、主题用 JS 配置对象即可完成、包体小（对比 Element Plus 的 SCSS 主题定制依赖与包体）。前端所有资源以本地依赖打包，不使用 CDN，保持完全离线可用。

### 服务启动与端口

未显式指定端口时，服务从默认端口起向上顺延，跳过被占端口直至绑定成功，实际地址以启动输出为准，消费方经环境变量对齐实际端口；显式指定端口时被占即启动失败、不顺延——显式表达的地址必须精确生效，不得被静默替换。

### 后端 API 契约

Web API 由 `refino-server` 实现、`@refino/ui` 消费。端点、payload 与状态码等形状以代码与测试为准，此处只记录跨包语义决策。

#### 服务端常驻索引架构

常驻索引由 `refino-storage` 的 Store 承载（见"存储层 Store"）：拓扑与摘要驻留内存，内容按需读取并缓存；增量更新、revision 计数与全量重建均为 Store 职责，Web 层只保留 HTTP 语义。

#### 画布按需查询

画布不默认全量加载（一个项目可能包含 10⁶ 量级的决策节点），以选择驱动按需展开：冷启动以全部根决策为锚点、不限下游代数地展开至工作集上限，作为画布初始内容。画布口径的根决策指 grounds 不含决策节点的决策（较治理口径的"grounds 为空"更宽，使顶层决策均落在前提上的图仍有冷启动入口）。工作集为积累式：选中节点的展开块并入画布、已有内容不清空，总量达上限时按最旧访问淘汰未选中节点。查询端点均批量、部分成功（见"引擎提供的共享原语"）。

#### 外部变更同步

工具插件经 `refino-storage` 直接写入 `.refino/`，不经过 web 服务，服务端索引必然与磁盘漂移。同步机制：监听分片目录、事件按安静期去抖后批量应用（API 写入与外部文件事件走同一索引更新入口）；revision 单调递增，经 SSE 向客户端推送变更并标注来源（界面/API 写入或外部文件事件）；SSE 断线重连后按当前 revision 全量比对刷新；手动刷新保留为权威重建通道。节点历史（经 git 提供节点级 log/diff）是后续课题，单独立项。

#### 编辑冲突处理

编辑器打开节点时记录 base 快照，外部变更到达该节点时：无改动则静默更新；有改动且外部只改了用户未动过的字段则静默字段级合并并轻提示；外部改了用户同一字段则提示冲突、二选一（载入外部版本，或保留我的改动、保存时覆盖）。乐观并发控制：保存可携带打开时记录的 revision，服务端保存前比对，不一致即拒绝，防止用户在冲突提示后保存时再次被无声覆盖。

#### 读取语义

Web 读接口在图存在 issues 时照常返回数据并附带 issues，画布以问题角标呈现，不因瞬态无效状态阻塞浏览；CLI 查询则在存在 issues 时拒绝执行（结果有歧义）。

## 持续集成

verify（push/PR）覆盖 TS 全量门禁与 Rust 门禁（格式、lint、测试、wasm 目标编译检查）；release（`v*` tag）按平台矩阵构建，npm 与 crates.io 同 tag 双渠道发布。命令与平台细节以 workflow 文件为准。

## 测试工具

`@refino/testkit`：private 不发布，直接以 TS 源码作为 exports，各包以 devDependency 引入。Rust 侧在 Cargo workspace 内提供同构的 test-util（内存 Io 与 `.refino/` fixture 构造器），供各 crate 测试复用。
